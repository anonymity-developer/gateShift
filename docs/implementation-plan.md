# 2주 구현 계획

10작업일과 개발자 2명을 기준으로 잡았다. 아래 역할은 작업 분담 초안이다.

| 단계 | 백엔드·데이터 중심 | 프론트엔드·UX 중심 | 통합 완료 기준 |
| --- | --- | --- | --- |
| 1~3일차 · 기본 흐름 | Java 21/Spring Boot, MySQL 초기화, 여행·할 일·호텔 API, 운항 API 키와 샘플 응답 확인 | Vue/Vite 초기화, 여행 입력과 대시보드, 지도·카드에 사용할 데이터 형태 협의 | 화면에서 생성·편집한 여행을 새로고침 후에도 조회한다. |
| 4~7일차 · 핵심 기능 | 구역 경로와 탑승 기준 검증, 호텔 조건 추출·확인, 변경 대상 판단과 SSE | 시설 경유 지도, 호텔 근거 확인 화면, 변경 타임라인 | 지연·게이트 변경과 탑승 안내 정정 이벤트를 연속 재생한다. |
| 8~10일차 · 배포·검증 | 변경 중복·시간대 경계 검증, 배포, 실조회와 데모 기록 | 모바일 화면, 오류·빈 상태, 외부에서 열리는 발표 환경과 시연 구성 | 외부 URL로 시연을 처음부터 한 번 완료하고 검증 결과를 기록한다. |

## 우선 검증할 시나리오

| 항목 | 측정 방식 |
| --- | --- |
| 동선 안전 여유 | 정답이 있는 표본으로 불가능한 경유를 추천한 건수를 기록한다. 시설 마감, 이동 불가, 탑승 기준 미확인을 포함한다. |
| 조건 추출 | 호텔 예시 문구에서 마감 시각·연락 예외·원문 근거를 따로 채점하고 분모를 함께 공개한다. |
| 선택 재평가 | 게이트만 바뀐 경우 호텔을 재평가하지 않는지, 도착 시각만 바뀐 경우 공항 동선을 재계산하지 않는지 확인한다. |
| 변경 처리 | 동일 입력 재수신 시 변경 이벤트 발생 건수와 이벤트 입력부터 화면 갱신까지 걸린 시간을 측정한다. |

키 발급이나 호출이 늦어지면 공항 응답 예시와 이벤트 재생으로 통합을 진행한다. 발표 자료에는 실조회와 재생 결과를 구분한다. 모델 호출이 실패하면 수동 정책 입력으로 흐름을 이어간다.

초반에 API 요청·응답 예시와 상태 값을 공유한다. 두 사람은 대표 흐름 통합 리뷰를 함께 진행한다. 배포 호스팅, AI 모델 제공자, 최종 제출 평가표 반영은 해당 정보를 확인하는 단계에서 정한다.
